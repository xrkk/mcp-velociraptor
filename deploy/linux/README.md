# Loopback Linux deployment

`deploy-remnux.sh` invokes the production `deploy_remnux.py` with the system
Python standard library. It does not install dependencies, contact the Internet,
copy historical credentials or execute the historical test runner.

Download the official [v0.77.3 release](https://github.com/Velocidex/velociraptor/releases/tag/v0.77.3)
`velociraptor-v0.77.3-linux-amd64-musl.gz` on the host. Its SHA-256 is
`b4699d7ecfd5c0d656d86379e41f0eb34b0f12c3cb45398f1e747f10844d7930`.
The decompressed binary SHA-256 is
`93171158fa081c07e3dd6b2cfc194f1a1db3eb30861639ad16eae6092afa42f7`.
Copy the verified carrier and deployment entry to a new root-owned private guest
stage; pass the ordinary root-owned binary as `--binary`. No guest download occurs.

```sh
sudo ./deploy-remnux.sh --binary /root/vr-stage/velociraptor \
  --root /opt/velociraptor --datastore /var/lib/velociraptor \
  --transaction <uuid> --expected-uuid <verified-vm-uuid> \
  --expected-boot <verified-boot-id> --ready-seconds 90
```

Existing secure parents are required. Paths must be absolute, have no symlink,
root owner, no group/other writes and no overlapping installation/datastore.
Unknown paths, units, occupied ports, wrong binary or incomplete prior attempts
refuse. A completed same-transaction deployment is read-only reverified; it does
not regenerate credentials or restart services. This is not a migration or an
uninstall entry. A failed partial installation needs a separately reviewed
preservation/recovery action, never blind replay.

Configuration is generated by the actual pinned CLI. Client `server_urls`,
self-signed TLS and `writeback_linux` use the Client section. Server, client and
API credentials stay in root 0700 directories with 0600 files. Secret values
are neither printed nor hashed. Only 127.0.0.1:8000, :8001 and :8889 are configured;
there is no external listener or SSH-forwarding change. Both new systemd services
run as root with NoNewPrivileges and UMask 0077. The datastore is parameterized.

The deployment result requires active server/client, the local writeback client
registered as Linux and a working authenticated API query plus exact loopback
listeners. It distinguishes readiness from systemd start success. An exclusive
`deployment-<transaction>` record preserves parameters/failure phase and owned
unit cleanup results. On failure only the newly attempted units are disabled
and stopped; credentials, datastore and originals remain. These records are
persistent evidence, not disposable stage. Remove only the separately owned
input carrier stage after exact ownership/readback verification.

Run `.venv/bin/python -B -m unittest tests.test_linux_deployment` for local
command-double boundary checks. They do not establish native VM readiness.
The October 6/7 historical runner claims did not prove real seven-class triage
or actual high-granularity scope control. Production triage integration and
fresh native collections require their own acceptance; deployment alone does
not close those gaps. Windows native regression remains separate.
