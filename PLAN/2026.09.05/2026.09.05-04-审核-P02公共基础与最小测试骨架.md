## 5. 审核意见

### AUD-001｜fixture 不能替代真实产品的 ACC-003/008

- 首次轮次：`FULL-01`
- 来源层级：需求 `REQ-003/REQ-008`、`RACC-003/RACC-008`；总纲 `OUT-003/OUT-008`、`ACC-003/ACC-008`、P02 通过契约；方案第1章、第3.2节第10项、`ACC-P02-002/003/007/008`。
- 反例：按方案只修改 bridge 的 SDK 启动 hunk 并保留旧 78 工具时，真实 `tools/list` 仍包含 `list_orgs`、`client_info`、`list_clients`，以及大量 `org_id/client_id/hostname/os_filter` 参数；真实 handler 仍返回 JSON 字符串。专用 fixture 即使完全符合新契约，也不能证明真实产品 schema 无目标参数或所有产品工具只返回原生结构化结果。
- 证据：当前 `mcp_velociraptor_bridge.py` 的 `client_info/list_clients/run_vql/windows_*` 等注册及返回注解；方案明确旧工具迁移归 P03/P04，同时又宣称 P02 通过总纲 ACC-003/008。总纲只把“全部工具由 P06 终检”作为后序终检，没有把 P02 的产品责任改成 fixture-only。
- 风险：P02 可在产品仍违反根本接口不变量时被判通过，P03 得到虚假的前置门，P06 才暴露问题；七篇顺序门禁失真。
- 影响：P02 独立验收、P03/P04 入口、最终 RACC-003/008；共享目标和结果契约的唯一性。
- 最小闭合条件：必须在规范层明确“P02 只验证公共构件、ACC-003/008 产品完成另归后序”的正式责任变更，或让 P02 结束时的真实产品 `tools/list/tools/call` 已满足 ACC-003/008。不能仅以 fixture、内部模型或 README 中“迁移中”代替。
- 受影响既有通过项：总纲 v2 的 P02 通过条件、12.1 依赖闭合和 12.2 ACC 汇总；P01 的事实结论本身不受影响。
- 复审证据：真实 bridge 的完整 `tools/list` schema 差集、代表性真实 `tools/call` 成功/错误转录，以及 ACC-003/008 责任变更的已审核规范链或产品零差集证明。

### AUD-002｜真实 bridge 缺少 `tools/call`，无法覆盖 SDK 迁移的共享影响

- 首次轮次：`FULL-01`
- 来源层级：P01 报告第4、10章交接；总纲 `CON-004/OUT-029/ACC-018`；方案 `IMP-P02-001`、`ACC-P02-001/007`。
- 反例：server 可以 initialize 和列出工具后，在第一次真实调用时因返回转换、线程执行、同步 gRPC、schema 或异常包装失败。当前 P02 只对 fixture 做 `tools/call`，对真实 bridge 只做 initialize/list/关闭。
- 证据：P01 明确要求 P02 在真实 bridge 完成 initialize、tools/list、至少一个只读 tools/call、正常退出；方案把真实 call 从 ACC 中遗漏。官方 SDK v2.1.1 源码还表明 `-> str` 会默认触发结构化输出推导，因此仅替换 import/构造会改变现有 78 个 handler 的 output schema 和返回转换，不是纯启动变化。
- 风险：SDK 兼容修复可能只通过“可启动”而无法调用，或无意产生 JSON 字符串嵌套、文本副本及错误 schema。
- 影响：`IMP/ACC-P02-001/007/008`、README 过渡说明、全部旧工具在 P03/P04 前的共享运行态。
- 最小闭合条件：在真实 bridge 上至少调用一个只读 server 查询和一个代表性 endpoint 路径；断言实际 outputSchema、content、structuredContent、isError、stderr/stdout 和退出码，并明确 v2 对全部旧 `-> str` handler 的过渡影响。
- 受影响既有通过项：P01 向 P02 的 stdio 交接尚未被消费；P01 对旧入口失败的定性不受影响。
- 复审证据：锁定 2.1.1 官方 ClientSession 的真实 bridge 完整会话转录、子进程退出证据和 schema/result 快照。

### AUD-003｜缓存 client_id 不存在的生产信号没有证据或映射

- 首次轮次：`FULL-01`
- 来源层级：需求 `REQ-003/RACC-003`；总纲 `ACC-003` 前置与 `FB-001`；P01 报告；方案第3.2节第5项、4.2节、`IMP/ACC-P02-003`、`FB-P02-001`。
- 反例：注入后端可直接抛人工 `CachedClientIdNotFound` 并让单元测试通过，但真实 pyvelociraptor/VQL 可能以空结果、通用 gRPC 错误或 collection 失败表示不存在。若没有唯一识别规则，生产适配器要么永不刷新，要么把普通故障误判为目标消失。
- 证据：总纲要求 P01 已证明该信号；P01 报告只证明一个真实 client 及成功 Flow/Hunt，没有不存在 client_id 的请求、响应或错误分类证据。方案也没有给出从真实后端响应到专用异常的映射。
- 风险：缓存恢复核心 fallback 不可安全实现，可能换错目标或形成永久陈旧缓存。
- 影响：`TargetContext`、`CLIENT_ID_NOT_FOUND`、`ACC-P02-003/006`、P03/P04 所有 endpoint 操作。
- 最小闭合条件：在 Snapshot184 上以无副作用方式取得“明确不存在”的真实后端响应，冻结精确判据和适配器映射；证明离线、超时、普通 gRPC 与 collection 失败不匹配该判据。若后端没有可靠信号，必须触发受影响 REQ/ACC 的重新裁决。
- 受影响既有通过项：总纲 `ACC-003` 的前置陈述与 P02 入口完整性；不否定 P01 其他已通过事实。
- 复审证据：脱敏真实请求/响应、异常分类表、生产适配器测试及一次重试计数。

### AUD-004｜字节上限算法与公开 helper 签名不能同时成立

- 首次轮次：`FULL-01`
- 来源层级：`REQ-012` 公共切片、P01 四项限制、总纲 `ACC-012/018`；方案第3.2节第9项、4.1/4.3节、`IMP/ACC-P02-004/006`。
- 反例：`paginate_rows(rows, cursor, page_size)` 与 `limit_unpaged_rows(rows)` 只看到 rows，却要求按最终成功结构化对象计数。实际对象还含 operation、status、flow_id/hunt_id、pagination、warnings；这些可变字段加入后可把 helper 判定合格的页面推到 245554 bytes 以上。
- 证据：方案给出的函数签名没有完整包络或包络构造回调；“紧凑 UTF-8 JSON”也未冻结 `ensure_ascii`、分隔符、非 ASCII/转义字符、字段顺序是否影响证据口径。P01 的 245554 是实测 payload 候选，不自动定义新包络序列化算法。
- 风险：生产响应越界，或不同工具/实现得到不同截断点与 cursor，破坏数据一致性。
- 影响：所有分页和无分页结果、`ROW_TOO_LARGE`、P03/P04 复用接口及 ACC-004/006/012。
- 最小闭合条件：冻结唯一序列化口径，并让限制函数接收完整候选结构化对象或可重建最终包络的明确输入；测试最终 `structuredContent` 的实际 UTF-8 字节，包括非 ASCII、转义、长 ID/warning、分页元数据和恰好边界。
- 受影响既有通过项：P01 的数值证据继续有效，但其适用前提“包络显著变化时重裁决”已被触及，需要显式验证。
- 复审证据：算法伪代码/接口、边界向量、最终协议字节复算和多页合并哈希。

### AUD-005｜cursor 的 overflow、越界与结束语义没有唯一判定

- 首次轮次：`FULL-01`
- 来源层级：方案第3.2节第8项、4.1/4.3节、`IMP/ACC-P02-004`。
- 反例：Python 十进制整数没有自然溢出；`v1:999...`、`v1:01`、offset 等于或大于结果长度、cursor 指向已变化结果源时，当前方案无法推出应返回空终页、`INVALID_ARGUMENT` 还是其他稳定错误。
- 证据：方案只写“格式/负值/溢出”失败和“P04 绑定 source”，没有定义上界、规范编码、source 长度越界或终页规则；ACC 仅写“合法/非法 cursor”而无精确向量。
- 风险：实现者可作出多个不兼容实现；超长十进制还可形成不必要的解析资源消耗。
- 影响：`Pagination`、多页无漏重证明、P04 Flow/source 绑定及 `INVALID_ARGUMENT`。
- 最小闭合条件：冻结 offset 最大值/位数、前导零规则、offset==len、offset>len、空源、终页和源变化处理；列出可直接执行的输入—输出边界表。
- 受影响既有通过项：总纲只授权 P02 决定 cursor 编码，没有既有运行通过证据可沿用。
- 复审证据：规范表、解析器单元测试、超长输入资源上界和 P04 绑定消费样例。

### AUD-006｜合成 `SUBMITTED` 与“真实初始状态”共用一个 `status` 真值

- 首次轮次：`FULL-01`
- 来源层级：需求 `REQ-007/REQ-008`、`CON-005`；总纲 4.2、5.2、`OUT-007/008/030`；方案第4.1/4.3节、`ACC-P02-002/006`。
- 反例：collection 创建响应不含状态时，方案把 `SUBMITTED` 写入唯一 `status` 字段。调用方在 wire schema 中没有字段可判断这是 MCP 接受动作还是 Velociraptor Flow 状态，因而会把合成值当成后端初始状态。
- 证据：总纲要求动态启动返回“真实初始 status”，且 ID/状态来自后端；方案虽在文字中说 `SUBMITTED` 不冒充 Flow 终态，但数据模型没有状态来源或类型区分。
- 风险：状态生命周期产生第二真值；后续轮询、错误判断和审计记录可能混用操作态与 Flow 态。
- 影响：共享 SuccessResult、collection 原语、P03 动态工具、P04 固定启动工具及 RACC-007/008。
- 最小闭合条件：要么在创建后立即读取并返回真实 Flow 状态，要么在经规范重新裁决后用不同字段/类型明确区分“提交已接受”和“后端 Flow 状态”，并使 outputSchema 与测试可观察该差异。
- 受影响既有通过项：P01 只证明最终 `FINISHED` 及 Hunt `RUNNING/STOPPED`，没有为合成 `SUBMITTED` 背书。
- 复审证据：真实创建响应、随后的状态读取转录、最终 schema 和状态转换表。

### AUD-007｜稳定错误枚举缺少逐码触发、retryable 与脱敏映射

- 首次轮次：`FULL-01`
- 来源层级：需求 `REQ-008`；总纲 3.3、5.6、`ACC-008`；方案第3.2节第7项、4.1节、`IMP/ACC-P02-002/003/005`。
- 反例：同一个 gRPC status 可被实现者映射为 `CONNECTION_FAILED`、`BACKEND_TIMEOUT`、`BACKEND_ERROR` 或 `INTERNAL_ERROR`；`NOT_FOUND`、`CLIENT_NOT_FOUND`、`CLIENT_ID_NOT_FOUND` 的对象语义也可重叠。方案没有规定各 code 的触发谓词、retryable 值、允许 details 和未知异常兜底。
- 证据：P01 没有覆盖全部枚举的真实失败；方案直接冻结 12 个 code，只要求 fixture 为每个 code 造例，却没有生产映射表。`NOT_CANCELLABLE` 等主要由 P04 生命周期消费，更需要明确责任边界。
- 风险：所谓稳定 code 在 P03/P04 被不同解释，重试策略不一致，敏感异常文本可能进入 message/details。
- 影响：全部失败响应、缓存清理判定、README 错误说明和后序工具测试。
- 最小闭合条件：为每个 code 冻结 owning layer、精确触发条件、retryable、公开 details 白名单、原异常处理和相邻 code 排他关系；真实可构造项用 Win10VM 证据，剩余项用生产适配器受控返回验证并标注后序责任。
- 受影响既有通过项：总纲把具体枚举交给 P02；因此没有可沿用的既有枚举通过结论。
- 复审证据：错误决策表、真实/注入证据对应矩阵、秘密扫描和 SDK `isError` 转录。

### AUD-008｜统一 SuccessResult 强制无意义 null，弱化逐工具准确 schema

- 首次轮次：`FULL-01`
- 来源层级：需求 `REQ-008` 及 Q-060 当前有效结论；总纲 5.6；方案第4.1节。
- 反例：无 Flow 的 server 查询也必须返回 `flow_id:null`，无 Hunt 的调用返回 `hunt_id:null`，无分页语义的调用返回 `pagination:null`。这与“各工具只声明并返回自身适用字段，不强行填充无意义空字段”不一致，也会使一份宽 schema 取代准确的逐工具 output schema。
- 证据：方案将 SuccessResult 的七个字段全部列为必需；需求的当前有效 Q-060 明确只包含适用字段。
- 风险：调用方无法从字段存在性辨识能力，schema 过宽，后序工具容易把 null 当已知空值。
- 影响：公共模型、`ACC-P02-002`、P03/P04 每个产品工具 schema。
- 最小闭合条件：公共基类只固定真正全局字段；按操作组合适用字段并在序列化时省略不适用项，或对“全字段必需”进行正式需求重新裁决。
- 受影响既有通过项：总纲 v2 对“按语义提供、字段不适用不得伪造”的通过判断需随实现模型复核。
- 复审证据：各操作类型的 schema 样例、成功/空结果转录及不适用字段零出现断言。

### AUD-009｜`example.env` 是未纳入核心维护范围的实施落点

- 首次轮次：`FULL-01`
- 来源层级：送审核心维护范围、方案第1章、`IMP-P02-006` 与 `ACC-P02-008`。
- 反例：方案第1章核心范围没有 `example.env`，送审核心范围也未授权该路径；但 `IMP-P02-006` 把它列为实际落点。实施者无法判断应修改、保持过渡配置，还是留到 P07 清理危险开关。
- 证据：当前 `example.env` 含 `VELOCIRAPTOR_ORG_ID`、`VELOCIRAPTOR_DEBUG_VQL`、`ENABLE_DANGEROUS_TOOLS`；总纲把危险开关物理清理由 P07 负责，而 P02 只建立新公共层配置边界。
- 风险：越出本轮审核路径，或提前破坏旧工具/agent 的过渡配置；README 与配置样例相互失真。
- 影响：配置兼容、`ACC-P02-005/008`、P07 清理责任。
- 最小闭合条件：在实施前把 `example.env` 是否属于 P02 及允许修改的精确 hunk 与 P07 保留项明确一致；未正式纳入则从 P02 落点删除。
- 受影响既有通过项：总纲 P07 `OUT-015/ACC-015` 的危险开关清理时序。
- 复审证据：已审核范围表、该文件精确 diff 预期、两 README 与 P07 交接矩阵。

### AUD-010｜“完整 Windows lock”缺少集合等价和制品身份门禁

- 首次轮次：`FULL-01`
- 来源层级：`REQ-018/RACC-018`、总纲 `ACC-018`；P01 依赖证据；方案 `IMP/ACC-P02-001`、`FB-P02-004`。
- 反例：P01 记录 46 个 installed distributions，但 `attempt-003-pip-freeze.txt` 只有 45 行；若直接把 freeze 作为完整 lock，干净 venv 仍可因 bootstrap pip 或 wheel build 不同而与基线不等价。只检查 `mcp==2.1.1` 与安装成功也不能证明完整集合相同。
- 证据：P01 报告/平台证据的 distribution count 为 46，freeze 实算 45 行；方案没有规定 bootstrap 包政策、安装后规范化集合双向差集或 wheel hash manifest 的通过条件。
- 风险：所谓“完整 Windows 验收环境”在不同重建中漂移，SDK/schema 行为或间接依赖变化不能被门禁发现。
- 影响：`requirements.txt`、Windows lock、wheelhouse、`ACC-P02-001/007` 及全部后序测试可复现性。
- 最小闭合条件：明确 Windows lock 文件身份和 bootstrap 包是否纳入；安装后与冻结基线做名称+版本双向差集并要求为零（或记录唯一允许差异）；将实际 wheel 文件哈希/缺失检查纳入证据，而不只验证版本解析成功。
- 受影响既有通过项：P01 的 46 项事实与 wheelhouse 成功事实保持有效；P02 尚未证明 lock 等价。
- 复审证据：lock、wheel hash 清单、干净 venv 安装日志、安装前后集合差异为零及关键 import/stdio 转录。
