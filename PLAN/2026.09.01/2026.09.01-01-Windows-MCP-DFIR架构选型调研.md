# Windows-MCP 深度系统探查与恶意代码分析架构选型

> 调研日期：2026-09-01。范围是“一台交互式 Windows 恶意代码分析 VM，由 VM 外的 AI 操作”，没有批量送样或自动生成沙箱报告需求；本文也不提出内存镜像采集实施方案。资料只引用官方文档、官方仓库以及本次逐文件核对的五个候选仓库源码。

## 结论

1. **“只有一台 VM”本身不足以让 Velociraptor 成为默认首选；但本题已经提出的广义活体探查范围足以触发采用条件。** 如果只做少量同步查询，扩 Windows-MCP 最短；如果要同时覆盖进程/线程/模块/句柄/VAD、服务/驱动/网络、注册表/EVTX/NTFS、YARA 与文件采集，就不应在 Windows-MCP 重造整个 DFIR artifact/flow 层，应采用 Velociraptor。
2. **Volatility 3 与 Velociraptor 不是同类替代品。** Volatility 3 是面向已有内存镜像的结构重建/插件分析框架；Velociraptor 是面向端点的活体采集、远程调度、结果和上传工件平台。对“VM 外 AI 操作正在运行的 Windows”而言，Velociraptor 更像后端；Volatility 3 不提供 endpoint agent、采集调度或 flow。
3. **一旦选择 Velociraptor，就单独部署 Velociraptor-MCP adapter，不把 VQL、flow、Velociraptor client/server 或其结果存储塞进 Windows-MCP。** Windows-MCP 继续负责桌面/UI；adapter 负责 DFIR。
4. **在用户指定的五个仓库中，后续开发基座唯一选择 `mgreen27/mcp-velociraptor`。** 本结论重新从当前源码得出，只按“当前能力”和“可扩展性”同权评分；许可证、安全、成熟度和活跃度均未进入评分。它现有 78 个 MCP 工具，其中 35 个是 Windows 高层 wrapper，已经覆盖上述大部分活体/落盘证据面；其 `_run_collection_tool` / `_start_collection_tool` helper 使新增固定 artifact wrapper 接近机械工作。这最符合“AI 只填参数，减少 VQL/PowerShell 与工具发现 token”的目标。

```text
当前最小方案
AI ──> Windows-MCP ──> UIA / Win32 / native helper ──> VM 内 artifact 目录

采用 Velociraptor 后
AI ──┬─> Windows-MCP ───────────────────────────────> 交互桌面
     └─> 独立 Velociraptor-MCP adapter ──gRPC──────> Velociraptor server
                                                    └─> VM client
```

## 当前需求与落点

| 能力 | 范围 | 少量同步查询时 | 当前广义 DFIR 范围下 |
|---|---|---|---|
| 桌面交互 | 截图、UIA、点击、输入、操作调试器 GUI | Windows-MCP | Windows-MCP |
| 进程与内存视图 | 进程树、命令行、模块、线程、句柄、VAD、进程 YARA；必要时可并列提供指定进程转储 | Windows-MCP 结构化 wrapper + native helper | Velociraptor-MCP 高层 wrapper + 固定 artifact |
| 系统面 | 服务、驱动、网络连接、用户、任务计划、WMI 与自启动 | Windows-MCP 每项另做原生实现 | Velociraptor-MCP 高层 wrapper |
| 落盘取证面 | 注册表、EVTX、NTFS/MFT/USN、Amcache、Prefetch、Shimcache、SRUM、浏览器痕迹 | Windows-MCP 需引入多套 parser | Velociraptor artifact |
| 内容与文件 | 文件哈希/YARA、目标文件采集、结果 manifest | Windows-MCP 需自建采集/存储 | Velociraptor flow + filestore/upload |
| 长任务与结果 | 状态、取消、分页、断线后取回 | 当前不自研 | Velociraptor flow |

Windows-MCP 当前 `Process` 仅用 `psutil` 提供 list/kill，但工具层已有“一模块注册一个 FastMCP 工具，再委托 domain service”的扩展方式。[Process 工具](https://github.com/CursorTouch/Windows-MCP/blob/83e17f622597dd5b10a09fa34ffe0b8686dbc7eb/src/windows_mcp/tools/process.py)、[Process service](https://github.com/CursorTouch/Windows-MCP/blob/83e17f622597dd5b10a09fa34ffe0b8686dbc7eb/src/windows_mcp/process/service.py)。这适合补少量高频本地工具；但覆盖上表全部范围会同时要求 Windows API 封装、多个取证 parser、任务状态、文件传输和结果存储，已经越过 Windows-MCP 的自然边界。因此对用户当前列明的广义范围，正文后续以“独立 Velociraptor-MCP”为实施主线。

## Volatility 3 与 Velociraptor：详细能力比较

### 它们分析的“数据”不同

| 维度 | Volatility 3 | Velociraptor |
|---|---|---|
| 主要输入 | 已有内存镜像。CLI 的 `-f` 指定镜像，官方教程明确说明 Volatility 不负责内存采集。[Windows tutorial](https://volatility3.readthedocs.io/en/stable/getting-started-windows-tutorial.html)、[CLI](https://volatility3.readthedocs.io/en/latest/vol-cli.html) | endpoint 上的实时 API、进程内存、文件、注册表、NTFS、EVTX、WMI 等。官方说明 VQL 可以在一条 artifact 中组合文件、API 和 volatile source。[File Acquisition](https://docs.velociraptor.app/docs/file_collection/) |
| 数据抽象 | `Context` 容纳 memory layers、symbol tables、objects；automagic 识别内核映射和符号。它按地址层把物理/虚拟地址映射回来，再按符号解释内核对象。[Volatility basics](https://volatility3.readthedocs.io/en/latest/basics.html) | VQL plugin/function 提供数据行，YAML artifact 封装参数、precondition、一个或多个结果 source；server 编译 artifact 后下发客户端执行。[Artifacts](https://docs.velociraptor.app/docs/artifacts/) |
| 活体/离线 | 官方文档把常见使用方式定义为对静态镜像运行插件；Volatility 3 本身没有 Windows 常驻 agent 或远程任务面。[Windows tutorial](https://volatility3.readthedocs.io/en/stable/getting-started-windows-tutorial.html) | 主要做 live endpoint；同一 artifact 还可借助 accessor remapping 复用于 dead-disk 分析。[Artifacts](https://docs.velociraptor.app/docs/artifacts/) |

### Windows 取证覆盖面

**Volatility 3 的强项是从内存结构中重建状态，而不是调用当前 OS API。** 官方 Windows plugin 源码目录包含：

- 进程和跨视图：`pslist`、`psscan`、`pstree`、`psxview`、`cmdline`、`envars`；
- 用户态内存：`dlllist`、`ldrmodules`、`handles`、`threads`、`vadinfo`、`vadwalk`、`vadyarascan`、`malfind`、`hollowprocesses`、`processghosting`；
- 内核/驱动/网络对象：`modules`、`modscan`、`driverscan`、`driverirp`、`callbacks`、`ssdt`、`netscan`、`netstat`、`timers`；
- 从内存可恢复的系统痕迹：`filescan`、`dumpfiles`、`mftscan`、`shimcachemem`，以及 registry 子包的 `hivelist`、`hivescan`、`printkey`、`userassist`、`amcache` 等。

这些不是普通 inventory 查询：例如 `psscan`/`psxview`、pool scan 和 VAD/内核对象插件的价值，在于从镜像中扫描或交叉比对结构，不依赖目标系统此刻愿意通过正常 API 返回什么。完整清单见官方 [Windows plugins 源码](https://github.com/volatilityfoundation/volatility3/tree/develop/volatility3/framework/plugins/windows) 与 [registry plugins 源码](https://github.com/volatilityfoundation/volatility3/tree/develop/volatility3/framework/plugins/windows/registry)。

**Velociraptor 的强项是把多类活体证据放在同一查询和远程 collection 中。** Windows-only VQL 原语直接提供 `handles`、`modules`、`threads`、`vad`、`proc_yara`、`proc_dump`、registry、WMI、ETW 等接口；官方 artifact 库再把它们与文件、NTFS、事件日志和检测逻辑组合。[Windows-only VQL](https://docs.velociraptor.app/vql_reference/windows/)。典型范围包括：

- 活进程及其模块、句柄、线程、token、VAD、进程 YARA；
- 指定进程内存转储并作为 flow upload 返回，[Windows.Memory.ProcessDump](https://docs.velociraptor.app/artifact_references/pages/windows.memory.processdump/)；
- MFT、文件名痕迹和删除恢复线索，[Windows.NTFS.MFT](https://docs.velociraptor.app/artifact_references/pages/windows.ntfs.mft/)；
- EVTX IOC 查询和近实时事件监控，[EvtxHunter](https://docs.velociraptor.app/artifact_references/pages/windows.eventlogs.evtxhunter/)、[Client Monitoring](https://docs.velociraptor.app/docs/clients/monitoring/)；
- 注册表、持久化、Amcache、Prefetch、Shimcache、SRUM、浏览器、文件哈希/采集等磁盘与用户活动 artifact；
- VAD 范围过滤、内容 YARA 以及选定 section 上传，[Windows.System.VAD](https://docs.velociraptor.app/artifact_references/pages/windows.system.vad/)。

边界是：Velociraptor 对正在运行的进程可做很深的活体检查，但它通常不等价于 Volatility 对冻结镜像进行内核结构重建、pool scan 和跨视图分析。反过来，Volatility 也不等价于 Velociraptor 对当前磁盘、注册表、EVTX、WMI、ETW 与网络状态的统一远程采集。

### 扩展、调度和结果工件

| 维度 | Volatility 3 | Velociraptor |
|---|---|---|
| 扩展模型 | Python class 继承 `PluginInterface`，声明 requirements，返回 `TreeGrid`；插件可复用其他插件的 classmethod，也可通过 `--plugin-dirs` 增加/覆盖插件。[Writing a plugin](https://volatility3.readthedocs.io/en/latest/simple-plugin.html)、[CLI plugin dirs](https://volatility3.readthedocs.io/en/latest/vol-cli.html) | 常见扩展只需写 YAML artifact + VQL；artifact 可调用其他 artifact、包装外部工具，并可在 server 端更新而无需重编译/重部署 client。[Artifacts](https://docs.velociraptor.app/docs/artifacts/) |
| 本地结果 | 每个插件返回结构化 `TreeGrid`，CLI 可渲染为表格、JSON/JSONL、CSV/SQLite；产生的文件写到 output directory。[Basics/renderers](https://volatility3.readthedocs.io/en/latest/basics.html)、[CLI](https://volatility3.readthedocs.io/en/latest/vol-cli.html) | collection/flow 保存结构化 rows、状态、日志及上传文件；`upload()` 将 endpoint 文件关联到 collection 并存入 server filestore，`uploads()` 可再枚举。[File uploads](https://docs.velociraptor.app/docs/file_collection/) |
| 远程调度 | 无内建 client/server、队列、flow、hunt 或断线恢复；要由外层系统自行实现 | server 可向 client 调度 artifact collection；gRPC `Query` API 可由外部程序发起 collection 并读取结果。[Server API](https://docs.velociraptor.app/docs/server_automation/server_api/) |
| 多端点 | 无 | Hunt 对多个 endpoint 调度同一 artifact，并集中追踪和查询结果。[Hunting](https://docs.velociraptor.app/docs/hunting/) |
| 对 MCP 的意义 | 必须另写“文件输入 → plugin 参数 → renderer/文件输出”的作业适配层 | MCP adapter 可以直接映射 client、artifact、flow、result、upload；与本题的远程活体操作模型更贴合 |

所以，本题不应把 Volatility 3 当作 Velociraptor 的平替，也不应为了比较而引入新的镜像采集路线。**若需求只剩少数同步查询，可以做 Windows-MCP 最小扩展；按当前列明的广义 Windows DFIR 范围，应直接采用独立 Velociraptor-MCP。**

## 其他 DFIR 候选的边界

## 五个 Velociraptor-MCP 仓库的源码级比较

### 评分方法

只评两项，且同权重；这是**针对单台 Windows 恶意代码分析 VM**的基座评分，不是通用项目排名。

- **当前能力（5 分）**：现有源码对进程/线程/模块/句柄/VAD、系统/持久化/网络、注册表/EVTX/NTFS、YARA/文件采集提供了多少 AI 可直接填参的 Windows DFIR 高层工具，并考察 collection → result/upload 是否闭环。
- **可扩展性（5 分）**：新增一个高层 Windows 操作时，是否已有可复用 API client/helper、清晰的工具分层、类型化参数和可独立测试的边界。

许可证、安全、成熟度、维护频率、star/commit 数均不参与本节评分，也不用于选择结论。

### 唯一基座选择：`mgreen27/mcp-velociraptor`

重新核对源码后，`mgreen27` 胜出基于两项能力事实：

1. **当前能力**：它不是只暴露一个 generic `collect_artifact`，而是已经把 35 类 Windows 调查意图映射成工具参数。对相同调查，AI 可以直接调用 `windows_event_logs`、`windows_ntfs_mft`、`windows_usn_journal`、`windows_srum`、`windows_malfind`、`yara_scan_process` 等，不必先列 artifact、阅读参数、拼 VQL 再取结果。这直接对应用户观察到的 PowerShell/VQL token 成本。
2. **可扩展性**：现有 Windows wrapper 基本遵循同一模板，底层复用 `velociraptor_api.py` 及 collection helper；补 modules/threads/handles/VAD 等能力是机械扩展。需要做的结构改进是先拆分 2100 行 bridge，并补统一的 upload/manifest 层，而不是重写已有 35 类 Windows 能力。

在该基座上的第一轮改造应是：

1. 先把 `mcp_velociraptor_bridge.py` 按 `process_memory`、`system_network`、`persistence`、`registry_eventlog`、`ntfs_files` 拆分，共用 `velociraptor_api.py`。
2. 补齐强类型高层工具族：进程详情/模块/线程/句柄/VAD，服务/驱动/网络，注册表/EVTX/NTFS，YARA 与目标文件采集；工具内部固定 artifact，AI 只填业务参数。
3. 新增统一 `list_flow_uploads`、`get_artifact_manifest`、`download_flow_upload`，用流式落盘与同步哈希完成文件工件闭环；进程转储只是复用此闭环的一个并列 artifact 示例。
4. 对查询类响应统一分页、字段选择和 summary，避免把整张结果表推入上下文。
5. 保留通用 artifact collection 作为专家入口；日常路径优先高层 typed wrappers，从而减少 VQL/PowerShell 和工具发现 token。

## Windows-MCP 与 Velociraptor-MCP 的职责

| 情况 | Windows-MCP | Velociraptor-MCP |
|---|---|---|
| 仅有少量同步查询 | 只增加相应结构化 wrapper，例如进程、服务、网络或注册表查询 | 不部署 |
| 已决定采用 Velociraptor | 只保留 UIA、截图、输入、窗口和调试器 GUI 自动化 | 独立 fork `mgreen27/mcp-velociraptor`，负责广义 Windows DFIR、flow、result、upload |
| 出现长任务、断线恢复、上传工件、丰富 artifact | 不在 Windows-MCP 自研 queue/flow/filestore | 由 Velociraptor 原生 collection/flow/filestore 承担 |

若尚未采用 Velociraptor、只做小范围 PoC，Windows-MCP 也应按调查域暴露结构化语义，而不是把 shell 当通用后门：

```text
ProcessInspect(mode=inventory|details|modules|threads|handles|vad, pid?, filters?, page?)
SystemInspect(mode=services|drivers|connections|users|tasks|autoruns, filters?, page?)
RegistryQuery(hive, key, value_filter?, recurse?, page?)
EventLogQuery(channels, event_ids?, time_range?, text_filter?, page?)
NtfsQuery(mode=mft|usn|file, path_or_filter, time_range?, page?)
ContentScan(mode=file_yara|process_yara|hash, target, rules_or_hashes)
FileCollect(path, case_id?)
Artifact(mode=list|stat|hash|manifest, artifact_id?|path?)
```

所有列表/查询都应返回稳定字段、分页游标和摘要；所有文件型结果只返回 `artifact_id/path/size/sha256/created_at/status`，二进制不进入 MCP/LLM。成功判据是相同分析任务中 PowerShell/VQL 调用数、命令/输出 token 和重试数明显下降。

最终原则：**少量同步能力可以留在 Windows-MCP；用户已经列明的广义 DFIR 范围应由独立 Velociraptor-MCP 承担，并以 `mgreen27/mcp-velociraptor` 为唯一开发基座。Windows-MCP 管桌面，Velociraptor-MCP 管活体探查、取证 artifact 与结果工件。**
