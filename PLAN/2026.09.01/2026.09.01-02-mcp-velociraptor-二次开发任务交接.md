> 交接日期：2026-09-01

## 一、交接给新会话的任务结论

本任务已经完成选型，不需要在新会话中重新比较 Windows-MCP、C2 框架或其他 Velociraptor-MCP 项目。

后续开发应遵循以下结论：

1. **以 [`mgreen27/mcp-velociraptor`](https://github.com/mgreen27/mcp-velociraptor) 为唯一二次开发基座。**
2. **Velociraptor-MCP 保持为独立项目和独立进程，不合入 Windows-MCP。**
3. **Windows-MCP 继续负责 Windows 交互桌面；Velociraptor-MCP 负责广义 Windows 活体探查、取证 artifact、flow、结果和文件工件。**
4. **日常 AI 工具必须是高层、结构化、只需填写业务参数的接口。** PowerShell、任意 VQL 和任意 artifact collection 不应成为默认路径。
5. **进程转储只是众多活体/工件能力中的一个例子，不是项目主线。** 不得把设计再次收缩成“实现一个 dump 工具”。

推荐目标架构：

```text
VM 外 / 控制面
AI agent
  ├─ Windows-MCP connection ───────────────────────┐
  └─ fork 后的 mcp-velociraptor ── gRPC/mTLS ──> Velociraptor server
                                                    │
Windows 分析 VM                                     │
  ├─ Windows-MCP ──> UIA / screenshot / input      │
  └─ Velociraptor client <─────────────────────────┘
                         └─ collection results / uploaded artifacts
```

## 二、实际使用场景

用户在 Windows 虚拟机中运行分析环境，在虚拟机外使用 AI 智能体访问并操作虚拟机。分析对象通常是恶意代码，需要的是交互式、按需的深度系统探查与诊断。

目标能力不是某一个具体动作，而是以下完整范围：

| 调查域 | 目标能力示例 |
|---|---|
| 桌面交互 | 截图、UIA、点击、输入、窗口管理、操作调试器 GUI |
| 进程与内存视图 | 进程树、命令行、模块、线程、句柄、token、VAD、进程 YARA、必要时采集指定进程工件 |
| 系统与网络 | 服务、驱动、连接、DNS、用户、计划任务、WMI、自启动项 |
| 注册表与事件 | 注册表查询、EVTX 查询、PowerShell/登录/服务创建等事件 |
| NTFS 与执行痕迹 | MFT、USN、Amcache、Prefetch、Shimcache、BAM、SRUM |
| 文件与内容 | 文件查找、哈希、YARA、目标文件采集、元数据与 manifest |
| 长任务与工件 | flow 状态、结果分页、取消、上传文件枚举、下载、哈希和断线后取回 |

### 已明确不属于需求的内容

- 没有“批量提交样本并自动生成分析报告”需求。
- 不建设 CAPE/DRAKVUF 自动化沙箱路线。
- 不建设整机内存采集或整机内存镜像分析流水线。
- Volatility 3 只可能在未来已有内存镜像时作为独立分析 provider；它不是本次远程活体 DFIR 基座。
- 不基于 Sliver、AdaptixC2 或其他 C2 框架开发。
- 不把完整 DFIR agent、flow、filestore 或 Velociraptor 凭据塞进 Windows-MCP。

## 三、为什么选择 mgreen27/mcp-velociraptor

本轮选型只采用两个维度，并按同等权重判断：

1. 当前能力。
2. 可扩展性。

许可证、安全模型、社区活跃度、star、commit 数、发布成熟度等均没有进入这次选型结论。新会话不要用这些外围因素推翻已经确认的基座。

### 3.1 当前能力

调研时核对的上游提交为：

```text
repository: https://github.com/mgreen27/mcp-velociraptor
commit:     1f97a4f4e64d27faf07fe684d8cbfe270b57757d
```

该版本源码中存在 78 个 `@mcp.tool()`，其中约 35 个为 `windows_*` 高层 wrapper，已经覆盖：

- 进程和网络状态；
- 服务、计划任务、WMI、自启动；
- Amcache、BAM、UserAssist、Shimcache、Prefetch；
- MFT、USN、SRUM、EVTX；
- malfind、mutant、文件 YARA、进程 YARA；
- PowerShell、登录事件、浏览器与用户活动；
- hunt、通用 artifact collection、collection result、文件采集和 triage。

它与用户目标的关键匹配点是：大量调查意图已经被做成高层工具，AI 通常只需要填写 `client_id`、过滤器、时间范围、PID 或规则等参数，而不是先查 artifact 名称、读取 artifact 参数、组织 VQL，再解释通用结果。

### 3.2 可扩展性

上游已有可复用的基础层：

```text
mcp_velociraptor_bridge.py  # MCP tool schema 与大量 Windows wrappers
velociraptor_api.py         # gRPC、VQL、org、collection、flow/status/result helper
velociraptor_env.py         # 环境配置
```

以下 helper 已形成重复使用模式：

```text
_run_json_tool(...)
_run_collection_tool(...)
_start_collection_tool(...)
```

因此，新增一个“固定 artifact + 强类型参数 + 固定结果字段”的高层工具通常只是机械扩展，不需要重写 Velociraptor 连接和 collection 调度。

### 3.3 已知的开发缺口

选择该项目不代表直接原样交付。当前需要解决的主要缺口是：

- `mcp_velociraptor_bridge.py` 约 2,100 行，工具集中在单文件中；
- 现有工具数量很多，若全部默认暴露，会增加工具 schema 和选择成本；
- modules、threads、handles、VAD 等能力需要补充或聚合成稳定高层接口；
- 结果字段、分页、限制、摘要和错误格式尚未统一；
- 已有 collection/result，但缺少完整的 flow upload 枚举、manifest 和文件下载闭环；
- 大结果和文件工件不能直接进入 MCP/LLM 内容通道；
- 通用 VQL/artifact 能力需要与日常低-token 工具面分离。

## 四、目标产品形态

目标不是把上游 78 个工具原样再增加更多工具，而是构建两层工具面。

### 4.1 默认工具面：Windows 恶意代码分析

默认只向 AI 暴露少量按调查域组织的高层工具。建议初始接口如下，具体名称可在实现阶段基于上游兼容性微调：

```text
ClientResolve(hostname?, client_id?)

ProcessInspect(
  client_id,
  mode=inventory|tree|details|modules|threads|handles|token|vad,
  pid?, filters?, fields?, page?, page_size?
)

SystemInspect(
  client_id,
  mode=services|drivers|connections|dns|users|tasks|wmi|autoruns,
  filters?, fields?, page?, page_size?
)

PersistenceInspect(
  client_id,
  mode=services|tasks|wmi|startup|autoruns,
  filters?, time_range?, page?, page_size?
)

RegistryQuery(
  client_id,
  hive, key, value_filter?, recurse?, fields?, page?, page_size?
)

EventLogQuery(
  client_id,
  channels, event_ids?, providers?, time_range?, text_filter?,
  fields?, page?, page_size?
)

NtfsQuery(
  client_id,
  mode=mft|usn|file,
  path_or_filter?, time_range?, fields?, page?, page_size?
)

ExecutionEvidence(
  client_id,
  sources=amcache|prefetch|shimcache|bam|srum,
  filters?, time_range?, page?, page_size?
)

ContentScan(
  client_id,
  mode=file_yara|process_yara|hash,
  target, rules_or_hashes, options?
)

FileCollect(client_id, path_or_glob, case_id?, options?)

Flow(mode=status|results|cancel, client_id, flow_id, source?, page?, page_size?)

ArtifactFile(
  mode=list_uploads|manifest|download,
  client_id, flow_id, upload_name?, destination?
)
```

可以将某些高风险或低频动作做成独立工具，也可以把模式拆分，但必须优先考虑：

- 默认工具总数尽量少；
- 工具名直接表达调查意图；
- 参数 schema 稳定且无需模型构造 VQL；
- 结果可分页、可摘要、可继续获取；
- 文件内容永不直接进入模型上下文。

### 4.2 专家工具面

以下能力保留为专家或兼容入口，但默认工具 profile 不应暴露：

```text
RunVQL
CollectArtifact
ListAllArtifacts
HuntAcrossFleet
上游遗留的全部细粒度 wrapper
```

建议通过配置提供工具 profile：

```text
windows_malware_analysis   # 默认，精简的高层工具
legacy_windows             # 上游已有 Windows wrappers
expert_velociraptor        # generic artifact / VQL / hunt
all                        # 调试和兼容用途
```

这样既保留上游当前能力，又避免每次会话把全部工具 schema 发送给模型。

## 五、代码结构目标

建议把上游单文件桥接层拆成下列结构。实际包名可根据克隆后的代码风格调整，但职责不要重新混合：

```text
mcp_velociraptor/
  server.py                    # FastMCP 创建、transport、profile 选择
  config.py                    # 连接、结果限制、工件根目录、工具 profile
  models/
    common.py                  # Page、TimeRange、Error、ClientRef
    results.py                 # ToolResult、PagedResult、FlowRef
    artifacts.py               # ArtifactManifest、ArtifactFile
  tools/
    clients.py
    process_memory.py
    system_network.py
    persistence.py
    registry_eventlog.py
    ntfs_files.py
    execution_evidence.py
    content_scan.py
    flows.py
    artifact_files.py
    expert.py
  services/
    velociraptor.py            # 对现有 velociraptor_api.py 的收敛封装
    collections.py             # artifact mapping、collection 启动
    flows.py                   # status/result/cancel/pagination
    artifact_store.py          # upload 枚举、manifest、流式下载、哈希
  artifacts/
    mappings.py                # 高层 mode -> 固定 artifact/source/字段
  tests/
    unit/
    integration/
```

### 结构改造约束

- 第一轮重构保持上游现有工具名称和行为可回归验证，不要一开始就删除 78 个工具。
- 新高层工具与旧工具共用同一 service/helper，禁止复制两套 VQL 和 flow 实现。
- 高层工具内部只允许选择代码中登记的固定 artifact/source；不要让普通参数直接变成任意 artifact 名或 VQL 片段。
- artifact mapping 与 MCP handler 分离，便于替换 artifact 或调整字段而不修改 schema。
- 不要让 FastMCP handler 直接处理证书、gRPC channel、文件落盘或哈希细节。

## 六、统一数据契约

建议所有工具使用统一响应封套，避免每个 wrapper 返回不同风格的字符串：

```json
{
  "ok": true,
  "status": "complete",
  "client_id": "C.xxxxx",
  "flow_id": "F.xxxxx",
  "summary": {
    "returned_rows": 50,
    "total_rows": 231,
    "truncated": false
  },
  "page": {
    "cursor": "opaque-next-cursor",
    "has_more": true
  },
  "data": [],
  "artifacts": []
}
```

错误响应建议稳定为：

```json
{
  "ok": false,
  "status": "failed",
  "error": {
    "code": "CLIENT_OFFLINE",
    "message": "Client did not complete the collection before the deadline.",
    "retryable": true,
    "details": {}
  },
  "client_id": "C.xxxxx",
  "flow_id": "F.xxxxx"
}
```

至少统一以下错误码族：

```text
INVALID_ARGUMENT
CLIENT_NOT_FOUND
CLIENT_OFFLINE
COLLECTION_START_FAILED
FLOW_NOT_FOUND
FLOW_RUNNING
FLOW_FAILED
RESULT_SOURCE_NOT_FOUND
RESULT_LIMIT_EXCEEDED
UPLOAD_NOT_FOUND
DOWNLOAD_FAILED
DESTINATION_NOT_ALLOWED
ARTIFACT_NOT_AVAILABLE
BACKEND_UNAVAILABLE
TIMEOUT
```

### 分页和结果限制

- 所有列表型工具必须支持 `page_size` 和不透明 cursor，或与 Velociraptor 数据源匹配的稳定分页模型。
- 默认只返回调查所需的稳定字段，不默认返回 `*`。
- 返回结果必须包含摘要和是否截断。
- 不把长 VQL、完整 artifact 定义、完整 stdout 或无限结果表返回给模型。
- 时间戳统一为带时区的 ISO 8601；PID、偏移、大小等字段使用明确数值类型。

### 文件工件契约

文件型结果只返回 manifest：

```json
{
  "artifact_id": "case/flow/upload",
  "client_id": "C.xxxxx",
  "flow_id": "F.xxxxx",
  "source_artifact": "Windows....",
  "remote_name": "evidence.bin",
  "local_path": "/configured/artifact/root/...",
  "size_bytes": 123456,
  "sha256": "...",
  "created_at": "2026-09-01T12:34:56Z",
  "complete": true
}
```

二进制不得 base64 编入 MCP 响应。下载必须流式写入配置的 artifact 根目录，并在写入过程中计算哈希；不能先把完整文件聚合到进程内存。

## 七、建议实施阶段

### 阶段 0：建立独立开发仓库和基线

目标：获得可重复的上游基线，不修改 Windows-MCP。

任务：

1. 在用户指定的位置 fork/clone `mgreen27/mcp-velociraptor`；不要把其源码复制进 Windows-MCP。
2. 记录 upstream remote 与基线 commit `1f97a4f4e64d27faf07fe684d8cbfe270b57757d`。
3. 安装依赖并运行现有测试。
4. 启动 MCP，记录实际 `tools/list`、每个工具 schema 和工具总数。
5. 建立最小 Velociraptor lab 连接测试：client lookup、一个只读 collection、flow result。
6. 输出基线报告：可运行项、失败项、真实工具清单和后续重构影响面。

验收：

- 上游代码未被语义修改；
- 测试和 MCP 启动结果可重复；
- 新项目与 Windows-MCP 是两个独立仓库/进程；
- 已记录上游基线和环境配置方法，凭据未进入仓库。

### 阶段 1：无行为变化的模块拆分

目标：拆分 `mcp_velociraptor_bridge.py`，但保持现有工具的名称、参数和返回行为。

任务：

1. 引入 `tools/`、`services/` 和公共 models。
2. 按调查域移动现有 Windows wrappers。
3. 保持原工具注册结果一致。
4. 为公共 collection helper、参数转换和 VQL 构造补单元测试。
5. 增加协议级测试，比较重构前后的 `tools/list`。

验收：

- 旧工具清单和 schema 没有非预期变化；
- 旧测试通过；
- 新增的模块测试通过；
- 没有复制多份 gRPC/VQL/collection 实现。

### 阶段 2：统一结果、错误与分页

目标：让 MCP 返回稳定的机器接口，而不是面向 operator 的长文本。

任务：

1. 实现统一 `ToolResult`、`PagedResult`、`ToolError`。
2. 为高频查询增加字段选择、分页、摘要和限制。
3. 统一 client/flow/artifact 标识与时间戳格式。
4. 把 Velociraptor/gRPC/VQL 错误映射为稳定错误码。
5. 保持 legacy 工具兼容，新响应先用于新高层工具。

验收：

- AI 不需要解析自由文本来判断成功、失败、flow 状态或下一页；
- 大结果不会一次性进入上下文；
- 所有失败具有稳定 `error.code` 和 `retryable`。

### 阶段 3：默认高层 Windows 工具面

目标：覆盖广义活体探查，而不是围绕单一例子开发。

建议优先顺序：

1. `ClientResolve`。
2. `ProcessInspect`。
3. `SystemInspect`。
4. `RegistryQuery` 与 `EventLogQuery`。
5. `NtfsQuery` 与 `ExecutionEvidence`。
6. `ContentScan` 与 `FileCollect`。
7. `Flow`。

每个 mode 必须：

- 映射固定 artifact/source；
- 使用强类型业务参数；
- 声明返回字段；
- 支持过滤和分页；
- 给出稳定错误；
- 有 VQL/artifact mapping 单测和 MCP handler 测试。

验收：

- 常见恶意代码调查不需要 PowerShell；
- 常见路径不需要模型编写 VQL；
- 工具调用只包含业务参数；
- 工具数量和 schema 规模显著低于直接暴露全部 legacy 工具。

### 阶段 4：flow upload 与文件工件闭环

目标：让所有会产生文件的 artifact 共用可靠的工件通道。

任务：

1. 实现 `list_flow_uploads`。
2. 实现 `get_artifact_manifest`。
3. 实现流式 `download_flow_upload`。
4. 限制所有目标路径位于配置的 artifact 根目录。
5. 下载过程中同步计算 SHA-256，并记录完整性状态。
6. 将目标文件采集、日志包、进程相关工件等统一接入该通道。

验收：

- 文件不会进入 MCP 文本响应；
- 大文件不会完整驻留 MCP 进程内存；
- AI 可通过 manifest 查找、校验和继续处理工件；
- flow 运行中、失败、无上传物和下载中断都有稳定状态。

### 阶段 5：工具 profile 与 token 验证

目标：验证结构化工具确实减少模型成本，而不是仅把 PowerShell 换成任意 VQL。

任务：

1. 实现 `windows_malware_analysis` 默认 profile。
2. legacy/expert/all 工具按配置启用。
3. 设计一组固定调查任务，分别使用：
   - PowerShell/任意 VQL；
   - 上游原始工具面；
   - 新的默认高层工具面。
4. 记录工具 schema token、命令构造 token、输出 token、调用次数和重试次数。

验收：

- 默认 profile 能完成固定调查任务；
- PowerShell 和任意 VQL 调用显著下降；
- 总工具 schema、输出和重试成本低于直接暴露全部工具；
- 专家入口仍可按配置启用，没有丢失上游能力。

## 八、测试策略

至少包含以下测试层次：

### 单元测试

- 参数校验、时间范围、字段选择、分页 cursor；
- artifact/source mapping；
- VQL literal/escaping 和参数传递；
- Velociraptor 返回行到稳定 DTO 的转换；
- gRPC/VQL 错误到稳定错误码的映射；
- artifact 路径约束、manifest、流式哈希；
- 工具 profile 过滤。

### MCP 协议级测试

- `tools/list` 只出现当前 profile 的工具；
- schema 与预期快照一致；
- tool call 返回结构化 JSON，而不是无法判定的长文本；
- 分页和错误响应可由 MCP 客户端稳定解析。

### Velociraptor 集成测试

- client resolve；
- collection start；
- running/complete/failed flow；
- 多 source result；
- 分页或结果限制；
- upload list、manifest、download；
- client offline、artifact 不存在、flow 不存在。

### Windows 实验 VM 验证

至少覆盖以下调查链：

1. 定位目标 client。
2. 获取进程树并查看一个 PID 的模块、线程、句柄和 VAD。
3. 关联该进程的网络连接。
4. 查询服务、驱动、计划任务和 WMI 持久化。
5. 查询指定时间范围的 EVTX。
6. 查询 MFT/USN 与执行痕迹。
7. 对指定文件或进程执行 YARA/哈希操作。
8. 采集一个文件工件并通过 manifest/download 取回。
9. 恢复连接后继续查询已有 flow 和工件。

## 九、完成标准

项目达到首个可交付版本时，应同时满足：

- Windows-MCP 与 Velociraptor-MCP 职责清楚，没有重复建设完整 DFIR 层；
- 常规调查通过默认高层工具完成，不依赖 PowerShell 或任意 VQL；
- 覆盖进程/内存视图、系统/网络、持久化、注册表/事件日志、NTFS/执行痕迹、内容扫描和文件采集；
- 所有列表结果可限制、分页和摘要；
- 所有异步操作返回 flow id，并可继续查询状态和结果；
- 所有文件工件通过 manifest 和流式下载处理，不进入模型上下文；
- 默认工具 profile 明显小于上游完整工具面；
- legacy/expert 能力可选启用；
- 单元、MCP 协议、Velociraptor 集成和 Windows VM 验证均通过；
- 文档说明部署拓扑、配置、工具 profile、结果模型和常见错误。

## 十、实施时不要做的事

- 不要重新把任务理解为“实现进程转储”。
- 不要因为只有一台 VM 就继续把所有 DFIR parser 和任务系统塞进 Windows-MCP。
- 不要把 Sliver、AdaptixC2 或其他 C2 引入实现。
- 不要增加整机内存采集、Volatility 流水线或自动化沙箱。
- 不要默认暴露全部 78 个 legacy 工具。
- 不要把 PowerShell 或任意 VQL 包装成新的默认万能工具。
- 不要在 MCP 响应中返回二进制、大段 stdout 或无上限结果。
- 不要让下载目的路径越过配置的 artifact 根目录。
- 不要在没有基线测试的情况下先大规模重写上游。
- 不要修改 Windows-MCP 来承载 Velociraptor 的 client/server、flow 或 filestore。
