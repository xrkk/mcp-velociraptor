## 2. 新能力与旧契约的并存边界

注册面目标为 136 个精确名称：118 动态、12 原固定、6 本机传输。原 130 工具的名称、input/output schema、Velociraptor 唯一 client/endpoint、原 PacketCapture 排除及 DFIR 129 有效实测＋1 排除、五场 129×5＝645 关系全部原义保留。六工具属于 MCP 服务所在 Windows guest 授权根与 host 间的单任务文件传输，不收 `client_id`，不经 `target_context` 选择 Velociraptor endpoint，也不代表第二 VM。功能启用须受受保护 `VELOCIRAPTOR_TRANSFER_POLICY`、运行身份、guest 根、VM UUID/boot/epoch 与 ACL 的交集约束；缺 policy 时仍注册六工具，capabilities 只报 `enabled=false`，其他五个动作返回 `transfer_disabled`。坏 policy、身份不符或授权路径拒绝不得自动改选宽松 policy、另一 endpoint 或通道。正式入口维持 28790/mcp 的 Bearer、Host/Origin、会话和防火墙要求；stdio 仍仅作同注册实例内测。

六个工具的 wire 输入与 output 以采纳时锁定的 `velo_transfer/transfer_tools_schema.json` 精确字节及下表为规范附件；采用 Draft 2020-12 原始 JSON wire 验证，必须在 SDK/Pydantic 强制转换及 handler 副作用之前拒绝 extra 键、错类型、bool 当整数、整数当 bool、字符串冒充嵌套对象、显式 null 冒充缺席、方向/package 与 action/receipt 非法组合。错误不回显原入参、二进制或凭据。schema 更改须重新版本化、受影响验收和双适配器比较。

共享服务启动只复用既有 transport/API/metadata 前提并校验 136 名称、schema 与冲突；传输 policy/VM/ACL 在传输动作的相应授权门检查，不新增全服务启动门。`create_server()` 注册六名；`TransferToolService` 懒创建 guest service。缺 policy 时 capabilities 返回 disabled、另五项拒绝且不构造 guest identity/ACL provider；坏 policy、VM/boot/ACL 应拒绝传输而不使旧130的启动/调用条件额外收紧。T00 专门验这条隔离边，不能用整个 server 关停冒充坏 policy 传输拒绝。

## 3. 不可变任务、双向状态及恢复

host coordinator 是唯一全局业务入口和结果裁决者；普通调用者只给受限参数。解析并持久化初始 host 意图、`transfer_id`、方向、实际 source/destination、VM UUID/boot/epoch、通道、policy、预算与原 deadline，再构造 guest request。请求 digest 绑定完整不可变请求；终端绑定 K 还含 package size/hash、manifest hash。改变请求/意图必须冲突，不能改 ID 续跑。重启读原 journal、原 deadline 和身份；仅重试同 ID/同 digest/同 action/同 receipts，遇丢应答先 status/持久记录对账。`transfer_status` 可能在同一已登记任务上持久化已退出 worker 的 lease/owner 归位，或在 release 已授权且 owned worker 完成/停止后核验清理和目的并持久化终态；它不得创建新 begin/action/receipt、启动另一个业务 worker、清理未知对象或将未验证目的宣称完成。重复 status 必须复用原授权和原 deadline，终态幂等。`outcome_unknown` 不等于失败可另选通道；Velo→Windows fallback 只在 begin 前并满足明确只读探测条件，不因认证/Host/协议/身份错误或单次超时发生。Windows 控制面只承载固定 guest CLI，不能变为正式产品调用的 28787 代理。
本host coordinator是NON-009/OUT-048生产任务编排禁令的唯一、严格有界例外，只承接REQ-028已授权的一笔本机文件传输及原ID恢复/结果裁决；不得跨任务、发起自主调查、随机组合工具或成为通用生产编排器。P05/P06测试runner仍只执行声明式验收。

push：host 明确源集合、稳定身份与 producer/quiescent 证据→受限包及 manifest→guest begin→有界顺序 chunk→guest prepare 验包/注册 stage/目的前提→host 真实源验证后持久 source_validation receipt→guest commit 前持久 publish intent、原子独占发布、目的树复验并持久 publication receipt→guest release 先持久授权、只清理已登记 owned temp→host 再核 guest tombstone、目的、host cleanup 与证据，持久全局结果。pull：guest 源和 producer/epoch 验证、准备固定包→host begin/status/chunk 下载到受保护 partial→guest prepare 验源→host 独占发布并复验目的且持久 publication receipt→guest release 先持久授权再清理 owned source temp→host 再核 guest tombstone、host cleanup/目的和持久结果。每次 source 再验证使用内部 hash/identity；本规范不允许把结果声明当作物理核验。

取消、超时、进程死亡、网络断开、响应或 receipt 丢失均在原 journal/worker/intent/receipt 上恢复；deadline 不刷新。未知同名 stage/package/final 不覆盖、不认领、不清理；必须比较已登记身份与完整内容。publication 后任何失败保留 `published_ever=true`，不回滚删除成果；清理仅限自身持久登记对象，release 部分完成则 `cleanup_pending`，不得伪报 complete。全局 complete 必须持久化目的真实验证、guest 与 host 双端 cleanup、发布与请求绑定的收据、evidence index、最终 canonical result；结果落盘后才单行输出紧凑 summary 与 exit 0。rejected=2、incomplete=3、conflict=4、cleanup_pending=5 按实际持久状态，日志不得含 token、内容、全量 hash 列表。摘要可省去 AI 侧传输前后额外 SHA 命令和全量 hash 输出，但程序内部 chunk/package/manifest/source/destination/receipt 验证仍执行且原件入受保护 evidence；不新增每次人工比对。
