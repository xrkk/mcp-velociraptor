### 1.2 finally/清理失败不抹除证据（交接风险 5）

缺陷证据：`tests/p05_real_acceptance.py` 旧 finally 中任一 `trace_status`/`os_observation`/`close()` 抛异常时，`p05-real-acceptance.json` 完全不写出，此前全部采集丢失，且原始异常被清理异常替换。

修复：finally 全步骤改为逐段捕获并记录进 `evidence['final_observation_failures']`（应急 trace 清理、trace_after、network_after、stderr/sdk 关闭、raw_originals 计算）；证据文件无条件写出；`ok` 增加 `not cleanup_failures` 与 `trace_after` 存在性守卫；原始 failure 仍按 `from failure` 链保留。四链 parser 顶层增加对 `final_observation_failures` 非空的拒绝。

### 1.3 PID 0/4 空 CreationDate（交接风险 2）

缺陷证据：Win32_Process 对 PID 0（Idle）CreationDate 为 null（部分构建 PID 4 亦然）。旧实现在三处 PS 快照对 null 调 `.ToUniversalTime()` 直接抛错；Python 侧 `_parse_guest_processes` 对每行强制 `_parse_utc`、`select_protected_processes` 对 0/4 强制 `process_instant`、保护父链比较对 null 参与比较，均会崩或误拒。

修复：PS 三处（p05_real_acceptance.PS_PROCESS_SNAPSHOT、p05_ready_collect._guest_processes、_service 的 service_process_rows）改为 null 保留为 null；`_parse_guest_processes` 仅对 PID 0/4 允许 null（非空时仍须可解析）；`_verify_guest_process_semantics` 父链时间比较改为双方非空才比较（0/4 缺失时间不构成缺陷，保护集合仍保留 0/4）；`select_protected_processes` 仅对非 0/4 校验时间。

### 1.4 读取前逐级祖先 reparse 检查（交接风险 4）

缺陷证据：`p05_ready_collect._fixture_static` 旧 `Row` 只检查条目自身 reparse 位；祖先为 junction 时 Get-Item/Get-FileHash 会穿透重定向，读取先于任何祖先检查。

修复：新增 `Assert-ReparseFree`（按规范化绝对路径自驱动器根逐级 `Get-Item -Force` 并检查 ReparsePoint 位），在读取 spec/instance/marker/root 及每个 fixture 文件内容/哈希之前调用。

### 1.5 service_observation 祖先走查不再依赖 PSProvider（交接风险 1）

缺陷证据：`p05_service_observation` 旧 `Assert-P05PlainPath` 沿 `$cursor = $cursor.Parent` 上溯并读 `.PSProvider.Name`。`.Parent` 返回的 .NET DirectoryInfo 实例不携带 provider 附加属性，第二层起 `PSProvider` 大概率为 null，`$null -ne 'FileSystem'` 恒真，真实 Windows 上每条带父目录的路径都会抛 'reparse or non-filesystem path'。

修复：改为与 1.4 相同的逐级 `Get-Item` 字符串路径走查（驱动器绝对路径校验 + 每级 ReparsePoint 检查），完全不引用 PSProvider/.Parent；三个调用点改传 `.FullName`。该重写消除了对 PowerShell 属性适配细节的依赖，但仍需 Windows ParseInput + 真实只读运行确认（见 §3）。

### 1.6 四链 parser 拒绝带清理失败的记录

`verify_four_chain_core` 顶层成功判定增加 `final_observation_failures` 必须为空（与 1.2 呼应）。
