# Host transfer coordinator

`velo_transfer.host_coordinator.TransferCoordinator` runs one authorized host request through the selected transport, real host content store, journal, and publication layer. `await transfer(load_request(spec_path))` is the foreground Python entry. The command entry is:

```text
python -m velo_transfer --spec /absolute/path/to/request.json
python -m velo_transfer --spec /absolute/path/to/request.json --abort
```

The spec must follow `velo.transfer.request.v1` as documented in [host request](transfer-request.md). It supplies direction, explicit source and destination paths, connection profile, expected VM identity, evidence context, budget and transfer ID. Do not put credentials in the spec. `--abort` requires `resume:true` on the same spec path and original transfer ID. To resume, set `resume:true` while keeping the original request intent; the fixed journal and deadline are reused. A new transfer ID creates a separate task.

The CLI writes one small JSON object to stdout. A durable run returns an eight field summary with `schema=velo.transfer.result.v1` and `result_path` to the persistent detailed result. The current successful prefix returns `outcome=cleanup_pending` and exit code 5: guest release and destination proof can be complete, while host owned cleanup and global `COMPLETE` await T019. The host package, partial ledger and journal are retained. A command error returns `velo.transfer.command-error.v1` with a stable error code and no invented result path. An `exit_code` of 5 is therefore a reviewable prefix, not final completion.

The coordinator probes Velo first. Before begin, only confirmed `connection_unavailable`, `tools_missing`, or `capabilities_disabled` permit Windows fallback. Authentication, schema, identity and timeout errors do not. Once begin is attempted, the channel is stored and recovery probes that same channel. The peer UUID, boot identity, policy and build observations are pinned with the original request. A changed service instance does not stand in for a new VM epoch.

For push, the host captures a manifest and package, sends bounded chunks, obtains prepare, rechecks the actual source and package, persists the source receipt, then commits. For pull, it verifies a durable received prefix, checks the bundle and extracted tree, obtains prepare, and publishes the destination exclusively. Both directions require the release terminal, receipt and stopped worker; push checks guest destination proof and pull checks the actual published host tree. Every external call records an intent first. An uncertain mutation is reconciled with status for the same transfer ID and request digest. Operation IDs, input digests and original deadline govern recovery; a tool success alone cannot grant completion.

The coordinator keeps evidence for uncertain outcomes, transport cleanup paths, receipts and publication history. Multiple distinct adapter errors remain separately indexed, so a later status failure does not hide an earlier cleanup path or received publication receipt. It does not delete source, unknown residue or published destination on abort or failure. Inspect the persistent `result_path` and journal after an incomplete or conflicting run. The journal writer enforces single task access. Local tests in `tests/test_transfer_host_coordinator.py` exercise benign POSIX host files with a simulated guest terminal and injected adapter probes. These tests cover lost responses, fixed retry limits, a damaged received prefix, post-rename recovery, and a damaged published tree; they do not establish Windows VM, real MCP, deployment or large file acceptance. The host cleanup and global completion phase remain separate T019 work.
