# Host pull partial package (internal Linux API)

`HostPartial(journal: HostJournal, binding: dict)` receives a fixed pull package after the coordinator has persisted the complete K in `data.binding` and the exact pull `data.guest_request`. It validates those against the parsed `HostRequest`; the host intent digest is distinct from the guest request digest. All four methods run **inside** an existing `with journal.writer():` and require an existing journal task. The module never acquires another writer lock or selects a caller supplied path.

```python
from velo_transfer.host_partial import HostPartial

with journal.writer():
    partial = HostPartial(journal, complete_pull_binding)
    state = partial.initialize()          # or partial.resume() after a process restart
    state = partial.append(offset, chunk, chunk_sha256)
    package = partial.verify()             # only after all package bytes are acknowledged
```

`initialize()` and `resume()` return an independent dict with exactly `path`, `verified_offset`, `chunk_count`, and `ownership`. `append()` returns the same shape. `verify()` returns exactly `path`, `size`, `sha256`, `expected_manifest_sha256`, and `ownership`. `path` is the absolute private `received.part` path. `ownership` has `directory`, `received.part`, and `chunks.jsonl` entries. The directory entry has `path`, `device`, and `inode`; each file entry has `path`, `device`, `inode`, `size`, `mtime_ns`, and `ctime_ns`. These are observed identities for a later authorized coordinator cleanup, **not** cleanup authorization. The manifest digest is an expectation from K; this module does not unpack ZIP, validate the manifest/tree, publish a destination, release a guest source, or declare global completion.

The durable small journal field is exactly `data.receive_partial` with `schema: "velo.transfer.host-partial.v1"`, complete `binding`, `phase`, `directory`, `partial`, `ledger`, `verified_offset`, `chunk_count`, and `ledger_bytes`. `phase` is `DIRECTORY`, `PARTIAL`, or `READY`. The latter six fields record owned identities and the acknowledged data/ledger prefix. The two large files live only at `tasks/<transfer_id>/receive/received.part` and `chunks.jsonl` under the journal's private root; they never enter the immutable evidence directory. `receive` is mode 0700 and both ordinary single link files are mode 0600, current UID, with fixed names. Other journal data is preserved by loading the current revision and CAS saving only this field.

Initialization durably registers the new directory before creating the partial file, then registers the partial file before creating the ledger, then records `READY`. The directory is opened immediately after `mkdir`; its original descriptor identity is checked against the path after parent sync and again after journal registration. This narrows the observable registration window but does not claim atomic `mkdir` plus `open`. Each newly created file keeps its original exclusive-create descriptor open through parent sync and journal registration; descriptor, path, exact parent directory, UID, link count and mode must still match before and after persistence. A same-name replacement is rejected and left intact. A crash before an object's registration leaves an unknown same name that returns `partial_reconcile_required`; it is never adopted or removed by name. A registered `DIRECTORY` or `PARTIAL` stage can continue only when every registered identity still matches and the next path does not already exist. `READY` repeats through full `resume()`. Missing, replaced, linked or broadly accessible registered resources fail closed and are never rebuilt as a fresh task.

A new chunk must begin at the acknowledged offset, have nonempty `bytes`, a lowercase SHA-256 matching the actual bytes, and fit both the request chunk maximum and K package size. The implementation fsyncs package bytes, writes one canonical JSONL record `{offset,size,sha256}` and fsyncs it, then CAS saves the new offset/count/ledger byte boundary and observed identities. Only after that save returns does `append()` acknowledge. A repeat at an exact earlier chunk boundary rechecks both file identities against the durable ownership and the current append continuity observation before opening them; it then checks the ledger record and rereads the actual package bytes, and checks descriptor/path identity again before returning. Identical bytes on a new inode are rejected, as are mismatches and holes. A fresh instance first runs full prefix recovery; a continuing instance checks the recorded live identities and reruns recovery if they change. Explicit `resume()` always rehashes every acknowledged chunk from actual bytes, parses one bounded line at a time, checks the exact contiguous offset and ledger byte boundary, and refuses damaged acknowledged prefix. Only then may it truncate and fsync unacknowledged bytes or ledger tail on the same registered files. It never reads an unknown tail into memory, including a sparse tail beyond 4 GiB. This does not claim a real 4 GiB transfer test.

`verify()` performs that recovery and separately streams the complete package with the fixed deadline and budget checks. It independently compares the observed file size, complete stream byte count and K package size, then requires actual SHA-256 to equal K. A tail added after recovery cannot make a wrong-sized package valid even when its hash matches K; a replacement or content change during the read also fails. Opened descriptors are closed on failed identity observations, including when the second file of a pair fails to open. The request's original monotonic deadline is never extended. Package writes check free space including `min_free_bytes`; acknowledged ledger bytes are bounded by `max_metadata_bytes`. No package length proportional buffer is allocated. Stable `TransferContentError.code` values report ownership, binding, corruption, budget, deadline and IO failure without including file contents or external tool text. A successful package hash is only an input to the coordinator's later unpack, publication and release decisions.
