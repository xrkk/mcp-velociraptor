# Model Context Selection (shared client runtime)

The shared client in `agent_poc/velociraptor_mcp_runtime.py` gained two
context-facing capabilities: on-demand tool definitions and a bounded model
result view. Both live inside the existing `VelociraptorMCPClient`; no new
server tool, proxy, CLI or framework is registered, and the 137-tool registry,
permissions, approval gates and the transfer protocol are unchanged.

## On-demand tool definitions

`get_tool_definitions(allowed_tools=...)` now deep-copies each real
`Tool.input_schema` in full — `$defs`, local `$ref`, `oneOf`,
`additionalProperties`, constraints and defaults all survive; nothing is
trimmed to `properties`/`required` anymore.

- An explicit `allowed_tools` collection restricts the exposed definitions and
  fixes the set of names the model may actually execute in `chat` (see below).
  `[]` exposes zero tools. Duplicate names in a sequence are tolerated (set
  semantics); a bare string, or any non-string element, is rejected with
  `invalid_allowed_tools`; an unknown name is rejected with `unknown_tool`.
- With no explicit list (and no `default_allowed_tools`), the semantic is all
  available business tools — only an explicit list reduces definitions.
- The seven host `transfer_*` tools are never model-facing: the all-business
  list skips them, and an explicit list containing them is rejected with
  `host_transfer_required` pointing at the existing `velo_transfer` CLI.
  Host-side `call_tool_payload` can still call them; server-side safety gates
  are untouched.
- Selected tools keep the server's original order.

Tool metadata is loaded over the real SDK pagination
(`list_tools(*, params=PaginatedRequestParams(cursor=...))`, continuation from
`ListToolsResult.next_cursor`), bounded to 16 pages, rejecting repeated
cursors and duplicate tool names.

## Execution gate and round budget

Each `chat` call fixes the name set generated by that call's
`get_tool_definitions`. Both provider loops (Ollama and Azure OpenAI) check
every tool call name against this set *before* any MCP call: unknown,
not-exposed or host-transfer names get a bounded `tool_not_allowed` view as
the tool message (with `tool_call_id` kept where the provider supplies one)
and are never executed or retried. This is context selection, not a new
server-side authorization.

A new `max_tool_rounds` constructor argument (default 8, integer 1..32) bounds
the loop: after that many executed tool-call rounds, further tool calls stop
with a stable `model_tool_round_budget` result instead of looping forever.
Chats with no tools still produce plain summaries.

## Host payload adaptation (`call_tool_payload`)

The legacy host interface (`ok`/`data`/`error`) is preserved but now adapts
the real SDK `CallToolResult`: `structured_content` is authoritative,
`is_error=True` is never `ok`, fixed/dynamic results require
`operation == tool_name` and `status == "success"`, and transfer responses
follow their own `schema`/`status` envelope with `result`/`error` kept whole.
`data` carries the response's `data` when present, otherwise the full
structure; the complete `structured_content` is always returned alongside, so
pagination, warnings and identity are never lost. The legacy text path only
accepts a genuine old envelope (a dict with a boolean `ok`); any other text,
JSON without `ok`, or an operation/status mismatch is `protocol_error`, never
an implicit success. SDK exceptions surface as the stable `call_failed` code,
never an exception repr or credential material.

`client.last_tool_result` holds the full `model_dump(mode="json",
by_alias=True)` of the **most recent** call only, in memory, cleared before
each new call. It is not an archive: persist the full original yourself if
you need one. `call_tool_payload` never truncates rows or fields, never
paginates and never retries.

## Bounded model view (`call_tool`)

`call_tool` now returns a `velo.model.view.v1` JSON string bounded by
`model_result_max_bytes` (constructor default 16384, integer 1024..65536).
The view keeps `tool_ok`, `operation`/`status`, the real pagination fields
(`cursor`/`next_cursor`/`truncated`, `server_truncated` only when the source
has one), warning counts, error contents, plus row sampling controlled by
`model_result_sample_rows` (0..10, default 10) and `model_result_fields`
(None for whole rows, or up to 32 top-level field names). Rules:

- Only top-level fields of real `data` rows are projected; there is no eval,
  VQL or filter expression anywhere.
- Each sample row is at most 4096 UTF-8 bytes; an oversized row is omitted
  whole, never string-truncated into a fake-complete one.
- `rows_received` is the true list length; `sample_omitted_count` is
  `rows_received - len(final sample_rows)`, so rows kept out by the quota,
  the per-row limit or the total limit each count exactly once.
- Projection (field selection, or fewer samples than rows) sets
  `view_complete=false` even when the row count fits.
- Small responses may embed the complete structured payload; it is dropped
  (marked `payload_omitted`) once it would overflow.
- If even an empty-sample view overflows, a bounded fallback carries
  `view_error="model_view_overflow"`, the true `tool_ok`, and the error code
  only when it fits in 128 UTF-8 bytes (otherwise the stable `tool_error`
  with `error_code_omitted=true`). A tool success that merely overflows the
  view is not rewritten as a tool failure — `tool_ok` and `view_error` are
  separate.
- The view can report the canonical-JSON SHA-256 and byte size of the raw
  response (`raw_sha256`/`raw_bytes`) but never fabricates a file path.

Model history receives only these bounded views; the full raw payload stays
available through `call_tool_payload` and `last_tool_result` for host-side
consumers (the existing agent keeps its full-data collection path).

## Boundaries

- `last_tool_result` is in-memory and single-slot; consecutive calls do not
  build an archive, and the model view is not an acceptance, archival or
  completeness proof. A page's `next_cursor=null` is not evidence that the
  whole collection or flow is finished.
- This is a reusable client capability. It does not force-deploy the
  historical agent example and does not make arbitrary external MCP clients
  gain these features automatically.
- Verified by bounded offline evidence with real SDK models and provider
  response stand-ins; no real network, model API, Windows endpoint or token
  cost was exercised.
