# Host transfer cleanup and completion

`HostCleanup(journal).clean()` deletes only the host temporary objects registered by the original transfer. The coordinator calls it after verifying the guest's released terminal, stopped release worker, publication receipt and destination proof. It uses the task's existing journal writer and original deadline. A true cleanup flag alone cannot authorize deletion.

For push, the only deletable object is the registered `tasks/<transfer_id>/push.zip`. Cleanup checks its exact file identity and package hash before unlinking it. The original source paths, unlisted siblings, journal and evidence stay in place. For pull, it first verifies the received package and contiguous ledger, then deletes the registered `receive/received.part`, `receive/chunks.jsonl` and empty `receive` directory. The staged tree has already been exclusively renamed into the final destination; a new object at the old stage name is treated as unknown residue and left untouched. The published destination is never a cleanup target.

Before the first deletion, the journal durably records `host_cleanup_intent` with the binding, publication receipt digest, task directory identity and exact targets. Cleanup preflights every registered file, directory and unknown member before deleting any target. It checks ownership again before each delete, calls unlink/rmdir relative to an opened parent directory, and syncs the parent. Missing registered targets count as already deleted only when the matching intent exists. A changed or extra object blocks recovery; no path is adopted just because its name or hash matches. After confirming all registered targets are absent and syncing the task directory, cleanup writes immutable `host_cleanup` evidence and records `host_cleanup_complete=true`. Repeated cleanup rechecks the same intent and returns the same proof without rebuilding temporary objects.

When the coordinator finishes local cleanup, pull verifies the published tree again. It then checks the original deadline and validates the complete result, writes immutable result evidence, and atomically records `result_ref`, `phase=COMPLETE` and completion attestations before returning `outcome=complete`, exit code 0. A local cleanup error retains the intent, registered paths, publication history and failure evidence and returns `cleanup_pending`, exit code 5. A damaged destination or proof conflict cannot become COMPLETE. Failure to write result evidence or to save the final journal revision cannot report a result path or completion. Expiry after cleanup returns an incomplete result under the original deadline.

Windows adapter control-file cleanup has separate ownership. `adapter_cleanup_pending` and recorded remote paths are retained for explicit verification; `HostCleanup` never deletes those paths by string and cannot claim completion while the flag is set. The local tests use benign POSIX files and a simulated guest terminal; they do not validate a real VM, MCP transport, Windows ACLs, or large-file performance. The filesystem checks are designed for registered objects and process crashes, and do not claim to defeat a malicious same-UID process racing filesystem changes. See [host coordinator](transfer-host-coordinator.md) and `tests/test_transfer_host_cleanup.py`.
