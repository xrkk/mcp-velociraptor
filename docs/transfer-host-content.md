# Host content preparation (internal Linux API)

`HostContent(journal: HostJournal)` provides synchronous `prepare_push()`, `verify_push_source()`, and `prepare_pull()`. The caller holds the same existing `journal.writer()` and has already created or loaded the task. The methods use the journal's original monotonic deadline through `request.content_budget`; they do not open a guest channel, authorize cleanup, publish, or declare global completion. The caller supplies a parsed protected spec and, for pull, the already fixed complete K and exact `guest_request`.

## Push

`prepare_push()` reads only the explicit source paths in the spec. A directory source includes its own tree; a file source does not include siblings. Each source parent is checked as a trusted ordinary chain and fixed by canonical spelling and directory device/inode. The existing content layer captures and later revalidates all file bytes, member names, directory identity and producer evidence references. The immutable manifest is stored with `journal.write_evidence("manifest", manifest)`, then `data.manifest_ref` and `data.host_push` are persisted before ZIP creation. The fixed package path is `journal.task_dir / "push.zip"`.

`data.host_push` uses `velo.transfer.host-push.v1` with exactly `schema`, `source_roots` (ordered `{path,device,inode}` records), `manifest_ref`, `package_path`, and `package_identity`. The last field starts `null` and becomes the actual `{device,inode,size,mtime_ns,ctime_ns}` after successful ZIP64 creation, full streaming hash, package parent directory sync and journal CAS save. `data.package` is exactly `{size,sha256,manifest_sha256}`. Repeated preparation reads the immutable manifest and verifies the fixed source, package inode and complete package bytes. `verify_push_source()` performs the same fresh checks for the coordinator's U3 timing; it never creates the initial manifest or package or writes a source validation receipt.

`prepare_push()` returns exactly `{package_path,package,manifest_ref,ownership}`. `verify_push_source()` returns exactly `{identity_digest,package,manifest_ref,ownership}`. `identity_digest` is the SHA-256 of canonical manifest JSON. `ownership` is `{path,device,inode,size,mtime_ns,ctime_ns}` for the actual local package. It is evidence for a later authorized cleanup decision, not cleanup authorization. Both results are independent copies; neither embeds the full manifest.

If a same-name `push.zip` exists before complete identity registration, the method preserves it and raises `host_package_reconcile_required`. This includes creation windows where the producer ZIP reached its final name but the parent sync or journal save failed. It never claims the object merely because its hash matches, and it does not scan or delete unknown temporary objects. A registered package that is missing, replaced, linked, mutated or nonprivate is rejected. Source changes after manifest capture never produce a revised manifest for that request. The caller must stop re-preparation after authorized package cleanup; the module will not rebuild a missing registered package.

## Pull

The caller persists `data.binding` as complete pull K and `data.guest_request` as the exact `make_guest_request` using `endpoint: host`, `identity: journal.binding.host_identity`, and the spec's canonical destination. `prepare_pull()` calls `HostPartial(journal, binding).verify()` and compares actual package bytes, size, hash and expected manifest digest with K before extraction. It refuses an existing formal destination. The actual destination parent is checked once as a trusted chain and pinned by directory device/inode. Its exact path is the only allowed root; no external parent is created.

`data.host_pull` uses `velo.transfer.host-pull.v1` with exactly `schema`, `stage_name` (fixed `.velo-stage-` plus the first 32 hex chars of SHA-256 of transfer ID), `parent_identity`, and `extraction_complete`. The initial false record is persisted before `prepare_staging`. Its registration callback persists the exact four-field `data.staging` `{staging_directory,staging_identity,parent_identity,destination_directory}` before unpack writes any content. `unpack_bundle` verifies the fixed package and full staged tree; its returned manifest digest must match K. The manifest is stored as immutable journal evidence, `data.manifest_ref` and exact `data.package` are saved, and only then is `extraction_complete` set true. Return shape is exactly `{staging,package,manifest_ref}`, with an independent copy.

An intent with a same-name stage but no registered identity raises `stage_reconcile_required` and leaves it intact. An incomplete registered stage is preflight scanned under file count, metadata, deadline, private identity, ordinary node and single-link gates. Any link, hardlink, FIFO or other special object, or replacement fails before deleting stage content. Once fully checked, only registered stage children are cleared in postorder, never the stage root; the same inode is then unpacked from the original verified package. The preflight records stable directory device, inode, owner and mode. Each deletion rechecks the directory chain against those fields; it does not treat the directory size or mtime change caused by removing its own children as a replacement. Files retain strict device, inode, size and mtime checks. A completed stage is freshly checked with `verify_tree` and cannot be silently repaired. `publish_intent`, `publication_receipt` or `published_ever` forbids another prepare; publication recovery belongs to `HostPublication`. The package, original source, formal destination and evidence remain untouched by this module.

The local tests use benign Linux files, injected errors and an actual `HostPartial` chunk ledger. They do not prove a 4 GiB transfer, guest execution, Windows ACL behavior, global receipt reconciliation or deployment.
